# git-pr — 브랜치의 커밋을 모아 PR 생성

## 절차

1. **사전 점검** — 하나라도 어긋나면 이유를 알리고 멈춘다(임의로 고치지 않는다).
   - `gh`가 없으면 `brew install gh` 후 `gh auth login`을 안내하고 멈춘다. 설치는 직접 하지 않는다.
   - 현재 브랜치가 `main`이면 멈추고 사용자에게 브랜치 이름을 묻는다(이름은 먼저 묻기, `feat/<m>-<topic>`).
   - 작업 트리가 깨끗해야 한다. 변경이 남아 있으면 `/git-commit`을 먼저 하자고 알린다.
   - 같은 브랜치의 열린 PR이 있는지 `gh pr list --head <브랜치>`로 본다. 있으면 그 URL을 알리고 멈춘다.
2. **분석**: 베이스는 `main`. `git log main..HEAD --format='%h %s%n%b'`, `git diff --stat main...HEAD`로 커밋과 변경 범위를 읽는다.
   커밋이 0개면 멈춘다.
3. **제안**: 제목과 본문을 보여주고 확인받는다. 푸시가 필요한지(원격에 브랜치가 없거나 뒤처짐)도 함께 알린다.
4. **실행**: 승인되면 푸시 → PR 생성. 푸시는 외부에 공개되는 동작이라 3의 승인 없이는 하지 않는다.
   ```
   git push -u origin <브랜치>
   gh pr create --base main --head <브랜치> --title "<제목>" --body-file <본문 파일>
   ```
   본문은 스크래치패드의 임시 파일에 써서 `--body-file`로 넘긴다(셸 인용 문제 방지).
5. **보고**: PR URL, 제목, 커밋 수. 머지·리뷰어 지정·라벨은 요청 시에만 한다.

## 제목

`[type] scope — 한국어 한 줄 요약` (git-commit과 같은 형식).
- 커밋이 하나면 그 커밋 제목을 쓴다.
- 여럿이면 가장 큰 변경의 type과 브랜치 전체를 가리키는 scope(마일스톤이면 `M3`)로 쓴다. 70자 안팎.

## 본문 — 커밋 목록 중심

```
## 요약
이 PR이 무엇을 위한 것인지 1–2줄. 왜 필요했는지(마일스톤·문제)를 먼저.

## 커밋
- `해시` [type] scope — 제목 — 한 줄 이유
- …

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- 커밋은 오래된 것부터 순서대로 나열한다. 한 줄 이유는 커밋 본문의 "왜"에서 가져오고, 파일 목록은 쓰지 않는다.
- 요약에는 diff가 말해주지 않는 것(결정 번호, 남은 판단, 리뷰어가 볼 곳)만 적는다. 추가로 표나 섹션을 늘리지 않는다.
- 커밋에 포함되지 않는 로컬 산출물(`outputs/`, `work/`)은 PR에 없다는 점이 중요하면 요약에 한 줄로 적는다.
